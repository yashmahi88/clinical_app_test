# Deployment Agent

> **Generation notice.** This file was generated by `project-setup-agent` for the dev
> deployment target below. If the hosting or CI/CD setup changes, the generated sections
> must be regenerated and re-verified.

## Purpose
Take the merged commit from build to a verified running deployment in an allowed environment, and prove it works.

## Inputs
- `merge-result.json` (merge SHA)
- `plan.md` (rollout and rollback notes)

## Outputs
- `.agent/runs/<TICKET-KEY>/deploy-report.md`

## Invariant rules (static, always apply once generated)
1. Deploy only the **merge SHA** recorded in `merge-result.json`, built from the base branch, never from a feature branch.
2. Deploy only to environments listed in `deploy-targets`. **Production is disabled by default** and requires an explicit entry in `deploy-targets` plus a recorded human approval.
3. Follow the order: build and package, deploy, post-deployment health checks, smoke tests, regression tests.
4. Every step must be evidenced (command, output, URL, version). A deployment is `succeeded` only when health checks and smoke tests pass.
5. On failure, run `rollback-procedure` immediately when its trigger conditions are met, then report `rolled_back` or `failed`. Never leave an environment half-deployed.
6. Never print, log or commit secret values. Use only the secret names in `secrets-and-access`.
7. Never modify CI/CD permissions, environment protection rules or infrastructure beyond what `deploy-procedure` defines.
8. Deployments must be idempotent: re-running for the same SHA must not create duplicates.

## `deploy-report.md` required fields
Environment, SHA, version or image tag, build result, deploy steps and results, health check results, smoke and regression results, rollback performed (yes/no), final status (`succeeded`, `failed`, `rolled_back`, `not_configured`), links to pipeline runs.

<!-- BEGIN GENERATED:deploy-procedure -->
For `dev` (idempotent — safe to re-run for the same SHA):

1. Fetch and check out the merge SHA on the deployment host: `git fetch origin && git checkout <merge-sha>`.
2. Install deps: `python3 -m venv .venv && .venv/bin/pip install -r requirements.txt`.
3. Stop any existing process serving port 8000 (`pkill -f 'uvicorn app.main:app'` —
   ignore "no process found").
4. Start: `CLINIC_DB_PATH=clinic.db nohup .venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port 8000 > uvicorn.log 2>&1 &`
5. Wait for readiness: poll `curl -sf http://localhost:8000/api/health` up to 30 s.
6. Run health and smoke checks (below), then record the deploy report.
<!-- END GENERATED:deploy-procedure -->

<!-- BEGIN GENERATED:health-and-smoke-checks -->
- **Liveness:** `curl -sf http://localhost:8000/api/health` → `{"status":"ok"}` within 30 s.
- **UI smoke:** `curl -sf http://localhost:8000/ | grep -q 'Clinical Appointment Manager'`.
- **API smoke (creates synthetic rows — acceptable in dev):**
  `POST /api/doctors` → 201; `POST /api/patients` → 201;
  `GET /api/appointments` → 200 JSON list.
- **Regression:** `.venv/bin/python -m pytest` on the deployed checkout → all tests pass.
- A deployment is `succeeded` only when liveness, UI smoke, API smoke and the pytest
  regression all pass.
<!-- END GENERATED:health-and-smoke-checks -->

<!-- BEGIN GENERATED:rollback-procedure -->
Triggers: liveness fails after 30 s, any smoke check fails, or the regression suite fails.

1. Stop the failed process: `pkill -f 'uvicorn app.main:app'`.
2. Check out the previous known-good SHA (recorded in the previous successful
   `deploy-report.md`; if none exists, report `failed` — do not guess).
3. Re-install deps and restart per `deploy-procedure` steps 2–5.
4. Re-run health + smoke checks. Report `rolled_back` if they pass, `failed` otherwise.
5. `clinic.db` is never deleted or reset by rollback; schema init is idempotent.
<!-- END GENERATED:rollback-procedure -->
